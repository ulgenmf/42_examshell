Inheritance and abstract classes Cluster: polyset-specific grammar — everything before this lesson still applies inside these classes too

Source: polyset's subject text (test/subs.txt). Classes involved: bag (abstract), searchable_bag (abstract, adds search), array_bag and tree_bag (concrete, each a different storage method), searchable_array_bag and searchable_tree_bag (must inherit from the array/tree implementation and implement the searchable_bag interface).

Declaring inheritance

Slot: class Derived : public Base { ... }; class array_bag : public bag { ... }; Rule: a colon after the class name, followed by public and the base class name, means every non-private member of bag is available inside array_bag as if declared there directly. Multiple base classes are comma-separated in the same slot: class searchable_array_bag : public array_bag, public searchable_bag { ... }; — required here since it must be both an array_bag and a searchable_bag at once.

Pure virtual functions — what makes a class abstract

Slot: ReturnType name(...) = 0; virtual void insert(int value) = 0; Rule: virtual marks the function as overridable by a derived class. = 0 at the end means this class declares the function exists but provides no body — no object of this exact class can ever be constructed (bag b; would fail to compile). A class becomes concrete (constructible) only once every inherited pure virtual function has an actual implementation somewhere in its inheritance chain.

Overriding in the derived class

Slot: ReturnType name(...) override; void insert(int value) override; Rule: same name and parameter types as the base class's declaration, now with a real body, in the derived class. override is not required by the language but should always be written: it makes the compiler verify this function really does match a virtual function in the base class — without it, a typo in the parameter list silently creates an unrelated new function instead of an error.

Calling the base class constructor

Slot: Derived::Derived(args) : Base(args) { } array_bag::array_bag(const array_bag& other) : bag(other) { ... } Rule: a colon after the parameter list, before the function body, lists which base-class constructor to run first, with what arguments. Every derived object's construction runs the base class's constructor first, then the derived class's own constructor body — this is where you route to the specific base constructor when there is more than one available (default vs. copy, same as lesson 1's overload rule, just one level up the inheritance chain).
Contrast: this changes nothing from lessons 1–10 — it adds one more layer Inside array_bag, searchable_bag, and set, construction (lesson 1), operator[]/access patterns (lesson 2), const (lesson 9, explicitly required by the subject: "Don't forget the const"), and the four-function set (lesson 10, explicitly required: "orthodox canonical form") all still apply exactly as already learned. Inheritance is one additional slot on top, not a replacement mechanism.
